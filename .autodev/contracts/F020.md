# F020 contract: patch HIGH/CRITICAL dependency vulnerabilities

## Why now (facts checked on `autodev/F020`, 2026-11-16)
- `vuln_watch.py .` reads the lower bound of every range in `pyproject.toml` ("range-allows"). Before: 26 HIGH/CRITICAL findings on torch, transformers, fastapi, aiohttp, black, starlette (`evidence/F020/before.txt`). No lockfile or requirements file exists, so `pyproject.toml` is the only manifest.
- Every fixed release needs Python >= 3.10 (torch 2.10.0, transformers 5.10.0, starlette 1.3.1, aiohttp 3.14.4, black 26.x; checked on PyPI JSON). The core declares `requires-python >= 3.9`.
- `fastapi 0.109.1` (the version named in the acceptance text) pins `starlette<0.36`, which conflicts with the required `starlette>=1.3.1`. The first fastapi without an upper bound on starlette is `0.133.0` (checked: 0.129.0 has `<1.0.0`, 0.133.0 has `>=0.40.0`).
- Only `fastapi`, `torch` and `transformers` are imported by the code: `web/server.py`, `core/enhanced_inference_engine.py`, `models/advanced_models.py`, `web/interface.py`.

## Scope
Changes: `pyproject.toml` (extras `web`, `ml`, `dev`), `CHANGELOG.md` (Security entry), this contract and its evidence.
Does not change: `requires-python`, core dependencies, source code, tests, CI workflows, the public contract snapshot.

## Decisions
- **D-markers.** Patched pins carry `python_version >= '3.10'`. Alternative rejected: raising `requires-python` to 3.10. It would change the public package metadata, the CI matrix (F003) and the classifiers for a library whose core does not need it. Consequence: on Python 3.9 the three extras install none of these packages, so nothing vulnerable is installed there. The scanner still sees the floor and reports clean.
- **D-fastapi.** `fastapi>=0.133.0`, not the `0.109.1` named in the acceptance text, because 0.109.1 is incompatible with the starlette fix.
- **D-black.** `black>=26.10.1`: GHSA-cg8m-r9f2-5wm2 is fixed only in 26.10.1 (the acceptance text lists 26.3.1).
- **D-multipart.** `web/server.py` uses `UploadFile`; FastAPI raises `RuntimeError` at import without `python-multipart`, and no extra declared it (a failure that predates this feature). It is added with the floor `0.0.31`, the lowest release past all seven advisories the scanner lists.

## Done means
- **D1 (acceptance 1).** `PYTHONIOENCODING=utf-8 python ${CLAUDE_PLUGIN_ROOT}/tools/vuln_watch.py .` prints 0 lines with `CRITICAL` or `HIGH`. Evidence: `before.txt` (26 lines) and `after.txt` (empty), full outputs in `before-full.txt` and `after-full.txt`. (The tool crashes on Windows with the default cp1252 console; the UTF-8 variable is a workaround, not a tool fix.)
- **D2 (acceptance 2).** Project test command on the `.venv` from `project.toml`: 1026 passed, 22 skipped, 10 xfailed, same as the baseline (`suite-base-venv.log`). The same suite in a venv built from `.[dev,cli,web,ml]` on Python 3.11 resolved to torch 2.15.0, transformers 5.23.0, fastapi 0.163.1, starlette 1.10.0, aiohttp 3.14.5: `suite-extras-venv.log`. `uv pip compile` of all floors on Python 3.10 and 3.11 resolves without conflict. `ruff check src tests` clean.
- **D3 (acceptance 3, breaking upgrades).** In the extras venv: `geneforgelang.core.enhanced_inference_engine` imports with `HAS_ML_DEPS True` (a failed transformers import would be silent there). `web/server.py` imports and answers over HTTP through `fastapi.testclient.TestClient` (`http-smoke.txt`: `/health` 200).
- **D4 (no vulnerable package left).** None left. Moderate and low findings are out of scope.

## Verification channel
CLI only: the scanner, pytest, ruff, `uv pip compile`, `TestClient` against the real app.

## Assumptions (falsifiable)
- A1. The scanner reads the floor, not the resolved version. Falsify: it flagged `black==26.3.1` after the first bump, then `python-multipart==0.0.20`.
- A2. No code uses a removed torch/transformers API. Falsify: D3 import check and the extras suite.
- A3. Python 3.9 users of the extras lose these packages rather than get vulnerable ones (marker semantics in PEP 508).

## Findings, not fixed here (outside scope)
- `web/server.py` and `models/advanced_models.py` import from a package `gfl` that does not exist, so every endpoint except `/health` answers 503 and the advanced models cannot import. Candidate for F013 (decides whether the HTTP apps stay).
- `vuln_watch.py` crashes on non-cp1252 characters in advisory summaries when the console is cp1252.

## Out of scope
- Moderate/low advisories (pydantic, pytest, requests, scikit-learn, starlette moderate). Lockfile creation. Dropping Python 3.9.

## Amendments after the evaluator review (`F020-review.md`)
All three gaps adopted and closed; evidence in `.autodev/evidence/F020/`.
- **R1 (build).** `uv build --wheel` succeeds; the wheel metadata carries the markers (`wheel-metadata.txt`: for example `torch>=2.10.0; python_version >= "3.10" and extra == "ml"`). D2 command list, exact: `uv run --no-project --python .venv python -m pytest tests -q -p no:cacheprovider --no-cov`; `uv run --no-project --python .venv ruff check src tests`; `uv build --wheel --out-dir <dir outside the repo>`.
- **R2 (A3, transitive risk on Python 3.9).** `uv pip compile pyproject.toml --extra web --extra ml --extra dev --extra cli --python-version 3.9` resolves to 81 pins and none of fastapi, starlette, aiohttp, torch, transformers, black, python-multipart (`resolved-py3.9.txt`): no transitive path installs them. A3 holds.
- **R3 (real ML code).** New `tests/test_transformers_model_real.py` runs `TransformersModel.load_model()` and `predict()` on tiny randomly initialised GPT-2 and BERT checkpoints saved to a temp dir (real torch and transformers, no double, no network) for `causal_lm` (the branch that passes `torch_dtype`) and `sequence_classification`. It asserts `prediction != "error"` because `predict()` swallows exceptions. Result on torch 2.15.0 / transformers 5.23.0: 2 passed. `torch_dtype` is still accepted and raised no warning in that run. The module skips itself when torch is absent (the project `.venv` has no ML extra), so the project test command shows one more skip.
- **R4 (resolved-set audit).** The scanner reads manifest floors only, so the resolved sets were audited with the same tool on a `requirements.txt` built by `uv pip compile`:
  - Python 3.11, extras `web`, `ml`, `cli` (73 packages, what an end user installs): **0 findings** (`audit-resolved-py3.11-nodev-full.txt`).
  - Python 3.11 with `dev` added: 1 HIGH, `filelock 3.32.7`, fixed in 4.2.1. `safety` (a `dev` tool) requires `filelock<4`. It is not installed for end users and no GFL code uses it.
  - Python 3.9, extras `web`, `ml`, `cli`: 1 CRITICAL `anyio 4.12.1` (fixed 4.14.2) and HIGH `urllib3 2.6.3` via `requests` (fixed 2.7.0 and 2.8.0). Every fixed release requires Python >= 3.10 (PyPI JSON), so no installable fix exists on 3.9. With `dev` added on 3.9 there are more (`nltk`, `authlib`, `cryptography`, `virtualenv` through `safety`), same cause.
  - Mitigation and decision: these are transitive packages, not among the six this feature names. Python 3.10 and newer installs are clean for end users. Python 3.9 is past its end of life and cannot receive fixes; dropping it from `requires-python` changes the public package metadata and the CI matrix, so it is left to the packaging features (F003, F011) and recorded in `progress.md`. The README and CHANGELOG now say that the extras install none of the pinned packages on 3.9.
- **R5 (evidence of deviations).** `before.txt` has the scanner lines for fastapi/black at the original floors. The scanner flagged `black==26.3.1` (GHSA-cg8m-r9f2-5wm2, fixed in 26.10.1) after the first bump, which is why the floor is 26.10.1. PyPI `requires_python` and `requires_dist` for the versions in "Why now" were read on 2026-11-16 from `https://pypi.org/pypi/<package>/<version>/json`.

## Results
- D1: `before.txt` 26 lines, `after.txt` empty (0 HIGH/CRITICAL).
- D2: base `.venv` 1026 passed, 23 skipped, 10 xfailed (baseline 1026/22/10); extras venv 1028 passed, 22 skipped, 10 xfailed; ruff clean; language check 0; wheel builds.
- D3: engine import `HAS_ML_DEPS True`; real model run passes; `web/server.py` answers `/health` 200 (`http-smoke.txt`).
- Not proved: behaviour of the HTTP endpoints other than `/health` (they answer 503 because of the missing `gfl` package, a defect that predates this feature); behaviour on GPU (`torch.float16` branch); Python 3.10 suite run (resolution checked, tests not run on 3.10).
