# `/neuroia` — NeuroIA Best Practices Protocol

> [!IMPORTANT]
> This workflow is **binding**. It must be applied to all write operations across the repository. There are no exceptions.

---

## Rule 0 — Repository Identification

Before executing any `git` operation, confirm the repository and branch:

```text
1. Which repo? → GeneForgeLang | GeneForge | neurodiagnoses-monorepo
2. Which branch? → NEVER work directly on `main`
3. Does it match the ongoing work?
```

> [!CAUTION]
> **NEVER mix changes across repositories.** Verify your local path before running any `git` command.

---

## Rule 1 — Branch Structure

```text
main          → Only receives merges via Pull Request. NEVER commit directly.
feature/*     → New features and capabilities (e.g., feature/rfoptimization-rescue)
fix/*         → Bug fixes                      (e.g., fix/tensor-contract-dimensions)
refactor/*    → Structural refactorings        (e.g., refactor/gftypes-decoupling)
experiment/*  → Technical exploration          (e.g., experiment/multimodel-consensus)
docs/*        → Documentation only             (e.g., docs/architecture-spec)
```

**Mandatory Flow:**
```text
feature/my-work → (reviewed PR & passing CI) → main
```

---

## Rule 2 — Mandatory English Language Standard

> [!IMPORTANT]
> **English is strictly mandatory across all code, docstrings, inline comments, commit messages, and documentation.** No exceptions.

---

## Rule 3 — Commit Conventions

Format: `type(scope): concise imperative description in English`

| Type | When to use |
|---|---|
| `feat` | New functionality or language primitive |
| `fix` | Bug fix |
| `refactor` | Code restructuring without behavioral changes |
| `docs` | Documentation updates |
| `test` | Adding or updating tests |
| `chore` | Maintenance tasks (deps, gitignore, configs) |
| `perf` | Performance improvements |

**Correct Examples:**
```text
feat(rfo): add candidate rescue lifecycle, multi-model consensus, and gfl-plugin-rfo
fix(types): resolve coordinate frame validation in TensorContract
docs(architecture): update comprehensive compiler specification
test(depmap): verify epistemic stop-gate on null co-dependency
```

> [!WARNING]
> Never commit: `.pyc`, `__pycache__/`, `.egg-info/`, `.env`, credentials, secrets, raw biological data (>10MB), or flat submodule pointers.

---

## Rule 4 — Pre-Commit Checklist

Before `git add`:

- [ ] Does `.gitignore` exclude build artifacts (`__pycache__/`, `*.pyc`, `*.egg-info/`, `.env`)?
- [ ] Are all code comments, docstrings, and docs strictly in **English**?
- [ ] Are all files free of credentials, tokens, or sensitive clinical data?
- [ ] Does every new piece of code have at least one automated test?
- [ ] Are you working on the correct feature branch (not on `main`)?

```bash
# Verify status BEFORE staging
git status --short
git diff --stat HEAD

# Stage specific files
git add src/ tests/ docs/ *.md pyproject.toml
```

---

## Rule 5 — Full Synchronization Process

```bash
# 1. Ensure you are on the feature branch
git checkout feature/my-work    # or git checkout -b feature/my-work

# 2. Add specific files
git add <specific-files>
git status --short

# 3. Commit with conventional English message
git commit -m "feat(scope): concise description in English"

# 4. Push to remote branch (NEVER to main)
git push origin feature/my-work

# 5. Open Pull Request via gh CLI
gh pr create \
  --base main \
  --head feature/my-work \
  --title "feat(scope): descriptive title" \
  --body "## Summary of Changes..."
```

## Rule 6 — Mandatory Continuous Self-Documentation

Whenever substantive developments occur (new types, AST blocks, contracts, plugins, mathematical/biological primitives), **you must document them immediately in the same turn** across:
1. `docs/architecture.md`
2. `docs/geneforgelang/plugins/PLUGIN_ECOSYSTEM.md` or feature specs
3. `CHANGELOG.md` under `[Unreleased]`
4. `docs/index.md` & `README.md`
Without needing explicit user reminders.

---

## Rule 7 — Strict Branch Protection & Quality Gates

- **Direct Commits Blocked on `main`**: All changes must land via Pull Requests.
- **Required Passing CI/CD Checks**: Tests and linting must pass before merging.
- **Peer Review**: At least one reviewer must approve.
- **Scientific Rigor**: Synthetic data mocking is prohibited in validation gates.
